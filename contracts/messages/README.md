# Message Contracts

Versioned inter-component message formats.

## v1: messages of pipwerk relay

Defined by the library `packages/relay-core` (package `pipwerk_relaycore`), described in [docs/technical/pipwerk-relay.md](../../docs/technical/pipwerk-relay.md).

| File | Content |
|---|---|
| `v1/message.schema.json` | the message: `id`, `sender`, `recipient`, `priority`, `kind`, `content`, `reference_id`, `created_at`, `attachments`, `receipt` |
| `v1/envelope.schema.json` | the envelope that lies on every transmission way: `format`, `body`, `link`; `$defs/Body` defines the JSON text in `body` |
| `v1/relay.receipt.schema.json` | the content of a message of the kind `relay.receipt`: empty |
| `v1/relay.undeliverable.schema.json` | the content of a message of the kind `relay.undeliverable`: `reason`, `text`, `recipient`, `kind` |
| `v1/probe.message.schema.json` | the content of a message of the kind `probe.message`: `text` |
| `v1/fetch.request.schema.json` | the content of a message of the kind `fetch.request` (the retrieval of market data, `components/pipwerk-fetch-mt5`): `broker`, `symbol`, `instrument`, `time_units`, `ticks`, `from`, `to` |
| `v1/fetch.file.schema.json` | the content of a message of the kind `fetch.file`: `name`, `data`, `rows`, `omitted`; the file is the attachment of the message |
| `v1/fetch.result.schema.json` | the content of a message of the kind `fetch.result`: `files`, `failed`, `error` |
| `v1/examples/` | valid examples: messages (`message-request.json`, `message-with-attachment.json`, `message-receipt.json`, `message-undeliverable.json`, `message-probe.json`), contents (`content-*.json`, among them `content-fetch-request.json`, `content-fetch-file.json`, `content-fetch-result.json`, `content-fetch-result-refused.json`), `envelope.json` |
| `v1/examples/invalid/` | invalid examples; every one is rejected by schema and model |

The schemas are generated from the models: `pipwerk-relaycore-schemas <directory>` writes them, `--check` reports a file that differs. The tests compare the files with the models and check that schema and model judge the examples and a series of border cases alike. The schemas of the kinds `fetch.*` are generated by the component that defines them: `python -m pipwerk_fetch_mt5.relay.schemas <directory>` (with `--check` it reports a file that differs), and its tests compare the files and judge the examples (`components/pipwerk-fetch-mt5/tests/test_relay_contents.py`).

### Envelope and check value

`body` is a text that holds the JSON of the body (`message`, `hops`, `stored`). A JSON schema validator cannot look into a text, so a reader parses `body` and checks the result against `#/$defs/Body`.

`link.mac` is HMAC-SHA256 with the key of the connection `link.from`, in lower case hexadecimal, over the UTF-8 bytes of

```
<link.from> LF <link.to> LF <body>
```

(`LF` is a line feed, `<body>` the text of `body` exactly as it is). Test vector: key `000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f`, `from` = `app-a`, `to` = `net1.relay1`, `body` = `{}` gives `e0e7f9f8af085df155f63c5ae69761d8dee65e349c2d9cf044ff44e107ee90a2`. This key belongs to the examples (`examples/envelope.json` is protected with it) and protects nothing.

A receiver checks `mac` before it reads `body`. `stored` is reserved for the attachments that go over a way for files; the first version of the library rejects an envelope in which it is set.

### Kinds of messages and their contents

The field `kind` names the kind of a message; `content` is a JSON object that follows the schema of the kind. The library knows three kinds and ships a schema for each; the content of every other kind is defined by the component that uses it. The retrieval of market data defines three (below); the library neither checks nor knows them.

| Kind | Sent by | Content |
|---|---|---|
| `relay.receipt` | the connector of the receiving component, after the component has stored a message that asked for a receipt | empty `{}`; `reference_id` is the id of the confirmed message; the priority is that of the confirmed message |
| `relay.undeliverable` | the relay at which delivery fails | `reason` (one of `sender_invalid`, `loop`, `unknown_recipient`, `unknown_relay`, `relay_unreachable`, `recipient_unreachable`, `too_large`), `text` (the fixed text of the reason, 1 to 200 characters), `recipient` (address of the recipient of the message that could not be delivered), `kind` (kind of that message); `reference_id` is its id |
| `probe.message` | the test component | `text` (1 to 1000 characters) |

A message of the kind `relay.receipt` or `relay.undeliverable` never asks for a receipt: `receipt` must be `false` (otherwise receipts of receipts would arise). The schema `message.schema.json` states this with `if`/`then`.

### Kinds of the retrieval of market data

`pipwerk-fetch-mt5 request` sends `fetch.request` to a running `pipwerk-fetch-mt5 serve`; `serve` answers with one `fetch.file` per file and one `fetch.result` at the end. All answers go to the sender of the request, with the id of the request as `reference_id`. None of the three asks for a receipt: the answer is the confirmation. Described in [docs/technical/pipwerk-fetch-mt5.md](../../docs/technical/pipwerk-fetch-mt5.md), section 16. Times are UTC with whole seconds and a trailing `Z`; every content rejects additional fields.

| Kind | Sent by | Content |
|---|---|---|
| `fetch.request` | `request` | `broker` (name of the trade server MetaTrader 5 is logged in to), `symbol` (symbol at the broker), `instrument` (optional designation of the files; without it the symbol), `time_units` (list of `M1` … `MN1`, may be empty), `ticks` (yes or no), `from` (included) and `to` (excluded) |
| `fetch.file` | `serve` | `name` (name of the file, equal to the name of the one attachment: `<designation>_<data>_<from>_<to>.json`), `data` (a time unit, `TICKS` or `CONTRACT`), `rows` (number of rows; not for `CONTRACT`), `omitted` (rows left out, by reason: `time_does_not_exist`, `double_local_time`, `duplicate_time`, `invalid_price`); the attachment is the file in the JSON format of the import (`contracts/market-data/v1/`) |
| `fetch.result` | `serve` | `files` (names of all files that were sent), `failed` (every part that could not be fetched: `data`, `from`, `to`, `code`, `text`), `error` (optional: `code` and `text` if the request as a whole was not carried out: `request_invalid`, `broker_mismatch`, `terminal_unavailable`, `broker_unknown` or `internal_error`; then `files` and `failed` are empty) |

Beyond the schema the model also checks: `from` lies before `to`, the years are 1970 to 2100, a time unit occurs once, the name of a file belongs to its `data`, a refused request has no files.

### Rules that only the model checks

- the names of the attachments of a message differ,
- `created_at` is a time in UTC (offset 0),
- `created_at` has the form of a time, and `id` and `reference_id` the form of a UUID: a JSON schema validator checks `format` only if it is told to (`format: date-time` needs an additional library in most validators).

The patterns end with `$`. In some regular expression dialects (for example that of Python) `$` also matches before a final line feed, so a validator may accept a name with a line feed at the end; the model rejects it.
