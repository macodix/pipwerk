# Glossar

## Dokumentstatus

- status: `accepted`
- zweck: Verbindliche Begriffe für alle Dokumente, Aufträge und Abstimmungen mit dem Auftraggeber. Jeder hier fehlende Fachbegriff wird bei seiner Einführung in einem Dokument definiert und hier ergänzt.
- stand: 2026-10-24

## Regeln

- Dokumente, Folien, Aufträge und Antworten an den Auftraggeber verwenden die Begriffe dieses Glossars. Ein Begriff wird nicht durch ein Synonym oder eine wörtliche Übersetzung aus dem Englischen ersetzt.
- Ein neuer Begriff wird beim ersten Auftreten erklärt: was er bezeichnet und wozu er gebraucht wird. Danach wird er hier eingetragen.
- Produktnamen von Werkzeugen und Bibliotheken werden beim ersten Auftreten in einem Text mit ihrem Zweck genannt.

## Fachliche Begriffe

Die fachlichen Objekte selbst sind im [Fachmodell](../design/domain/fachmodell.md) definiert. Hier stehen nur die Begriffe, die über das Fachmodell hinaus in Dokumentation und Oberfläche verwendet werden.

| Begriff | Bedeutung |
| --- | --- |
| Objekt | Etwas, mit dem ein Händler arbeitet, beschrieben im Fachmodell, zum Beispiel Strategie, Trend, Indikator, Regel, Regelwerk oder Order. Ein Objekt hat Eigenschaften, unabhängig davon, ob und wie es auf der Zeichenfläche dargestellt wird. Die Begriffe „Handelsobjekt“ und „fachliches Objekt“ werden nicht verwendet. |
| Objekttyp | Die Art eines Objekts, zum Beispiel „Regel“, „Trend“, „Indikator“ oder ein mitgelieferter Indikator wie „EMA“ oder „ZigZag“ (Fachmodell req-fach-013a, req-fach-054). Aus einem Objekttyp werden konkrete Objekte mit eigenen Parameterwerten angelegt. |
| Vorlage | Ein gespeichertes Objekt (Indikator, Trend, Regel, Regelwerk) mit Standardwerten. Beim Einfügen in eine Strategie entsteht daraus eine Instanz. |
| Instanz | Das Objekt, das beim Einfügen einer Vorlage oder eines Objekttyps in eine Strategie entsteht. Es ist eine vollständige Kopie: Es übernimmt die Standardwerte und den übrigen Inhalt der Vorlage, trägt einen in der Strategie vergebenen Namen (zum Beispiel EMA21), gehört nur dieser Strategie und nennt seine Herkunft. Eine Instanz kann auch in einer anderen Instanz oder in einer Vorlage enthalten sein (ein Indikator in einem Trend, eine Regel in einem Regelwerk). Zur Ausführung braucht sie ihre Vorlage nicht. |
| Herkunft | Die Angabe einer Instanz, woraus sie entstanden ist: der Objekttyp und, wenn sie aus einer Vorlage entstand, Kennung und Name der Vorlage zum Zeitpunkt des Einfügens (ein Name je Objekt, req-ui-016). Bei einem eingefügten Objekttyp (zum Beispiel `EMA`) fehlen Kennung und Name. Spätere Änderungen oder das Löschen der Vorlage ändern die Herkunft nicht. |
| Kennung | Der sprachneutrale Name eines Typs, einer Eigenschaft, eines Parameters, eines Ausgangs oder eines festgelegten Werts, in Dokumenten und Ausdrücken gespeichert (zum Beispiel `trendrichtung`, `stop_loss`, `flow.condition`). Kennungen von Eigenschaften, Parametern und Werten werden nach einer festen Regel aus dem deutschen Namen gebildet; die Oberfläche zeigt den Namen in der gewählten Sprache. Objekte und Elemente der Strategie tragen eine UUID als Kennung. |
| Namensraum | Die Menge der Namen, die ein Ausdruck an einer Stelle ansprechen kann. Alle Instanzen einer Strategie liegen in einem gemeinsamen Namensraum, auch Regeln, Regelwerke und Instanzen, die in einer anderen Instanz enthalten sind, zum Beispiel die Indikatoren eines Trends oder die Regeln eines Regelwerks. Über ihren Namen ist jede davon überall in der Strategie ansprechbar; verwendbar ist eine Instanz aber nur an Stellen, die eine Auswertung ausschließlich über die Stelle ihrer ersten Verwendung erreicht, an anderen Stellen bieten Bausteine und Verbinden sie nicht an (Fachmodell req-fach-055, req-ui-014). Die Order- und Positionsverwaltung gilt dabei als über ihr Element „Order aufgeben“ erreicht, auch mit eigenen Auslösern. Dazu kommen die Objekte der Anwendung und in einer Regel ihre Parameter. Ein Name darf in einer Strategie nur einmal vergeben werden; ein doppelter Name ist ein Fehler der Konsistenzprüfung. Ein innerer Name, etwa in einer enthaltenen Instanz oder ein Parameter einer Regel, verdeckt deshalb keinen gleichen Namen der Strategie (Fachmodell req-fach-055). Eine gespeicherte Vorlage hat für sich einen eigenen Namensraum aus ihren Parametern und ihrem Inhalt. Beim Einfügen einer Vorlage, die selbst Instanzen enthält, schlägt pipwerk Studio für jede davon einen Namen vor (req-ablauf-003). |
| Ausdruck | Text in der Formelsprache OpenFormula (eine Auswahl), der einen Wert berechnet: in einer Bedingung, Berechnung, Regel, Belegung oder eigenen Eigenschaft. Die Bibliothek zerlegt und prüft ihn, wertet ihn aber nicht aus. Namen stehen in Punkt-Schreibweise (`ema20.wert`), Argumente werden mit `;` getrennt. |
| Normalisierte Schreibweise | Die Schreibweise eines Ausdrucks, in der Namen die Schreibweise ihrer Kennung und Funktionen die Schreibweise der Norm haben (`order.VOLUMEN` wird zu `Order.volumen`, `if(…)` zu `IF(…)`). Alles andere bleibt Zeichen für Zeichen erhalten. Gespeichert wird sie. |
| nicht verfügbar | Der Wert eines Ausdrucks, wenn er eine Eigenschaft ansprechen würde, die das Objekt im Zusammenhang der Auswertung nicht hat, zum Beispiel `Order.limitpreis` bei einer Stop-Order oder `Position`, solange die Order noch keine Position hat (`#N/A` nach OpenFormula). Jede Rechnung damit ergibt „nicht verfügbar“; `ISNA` und `IFNA` fangen ihn ab. Die Wirkung bei der Ausführung steht in der technischen Dokumentation der gemeinsamen Python-Bibliothek. |
| leer | Der Wert einer Eigenschaft ohne Wert: eine Eigenschaft, die der Anwender nicht belegt hat (KANN), oder eine, die das Objekt gerade nicht belegt, zum Beispiel das vorletzte Hoch des `ZigZag`, solange er noch keine zwei Hochs gesetzt hat. Rechnen und Vergleichen mit „leer“ ist ein Fehler der Auswertung; `ISBLANK` prüft darauf. Ausnahme im Strategietester: Liefert ein Indikator zu Beginn eines Testlaufs noch keine Werte, gilt eine Bedingung mit diesen Werten als nicht erfüllt, die Auswertung bricht nicht ab (Anforderungen an den Strategietester, req-test-008). Nicht zu verwechseln mit „nicht verfügbar“. |
| Objekte der Anwendung | Konto, Instrument, Kerze, Tick, Order, Position und Strategie: Objekte, deren Werte das Handelssystem beziehungsweise der Strategietester bereitstellt. Ihr Objekttyp wird nicht vom Anwender gestaltet und nicht als Vorlage gespeichert. Konto, Instrument, Kerze und Tick können Parameter haben und mehrfach als Instanz verwendet werden. Order und Position bezeichnen in einer Regel die Order beziehungsweise Position, auf die die Regel angewendet wird, im Ablauf die Order und Position der Order- und Positionsverwaltung (Fachmodell req-fach-051). |
| Strategieparameter | Ein Wert oder ein Objekt, das an einer Stelle der Strategie festgelegt und überall in ihr verwendet wird, zum Beispiel die Handelszeiteinheit oder ein Instrument (Fachmodell req-fach-046). Im Ablauf wird er nicht geändert; er behält während eines Testlaufs oder einer Anwendung seinen Startwert (req-fach-047). |
| Element | Alles, was der Anwender auf der Zeichenfläche einer Strategie nutzt. Ein Element zeigt ein Objekt (zum Beispiel einen Trend) oder einen Teil des Ablaufs, der kein Objekt ist (Auslöser, Bedingung, Berechnung, Order aufgeben, Order ändern, Order löschen, Position ändern, Position schließen, Verbindung). Ob ein Element in mehreren Strategien verwendet werden kann, ist eine Eigenschaft seines Typs, kein eigener Begriff. Die Begriffe „Knoten“ und „Ablaufelement“ werden nicht verwendet. „Baustein“ bezeichnet kein Element, sondern einen Teil einer Bedingung oder Berechnung: einen Wert, einen Vergleich oder eine Verknüpfung (req-ui-015). |
| Elementtyp | Die Art eines Elements, zum Beispiel ein Objekttyp, „Bedingung“ oder „Order aufgeben“. |
| Assistent | Der geführte Aufbau einer neuen Strategie in pipwerk Studio: Nach „Neue Strategie“ führt er Schritt für Schritt durch Auslöser, Indikatoren, Bedingung und Order und kann jederzeit verlassen werden. In der Oberfläche heißt er nur „Assistent“, im Englischen „Assistant“ (Anforderungen an den Strategiedesigner req-ui-016). |
| Elementbibliothek | Der Bereich der Oberfläche, der die verfügbaren Elementtypen und die bereits angelegten Objekte zur Auswahl anbietet. |
| Auslöser | Ein Element, das festlegt, bei welchem Ereignis eine Strategie oder die Order- und Positionsverwaltung ausgewertet wird: Kerzenschluss einer Zeiteinheit, Tick, Manuell oder externes Ereignis. Ein Auslöser steht am Anfang des Ablaufs oder der Order- und Positionsverwaltung; „Manuell“ nur am Anfang des Ablaufs, nicht in der Order- und Positionsverwaltung (Fachmodell req-fach-053). Kerzenschluss und Tick haben den Parameter `Instrument`, vorbelegt mit dem Instrument der Anwendung (req-fach-053). Jede Auswertung beginnt an einem Auslöser. Eine Strategie kann Auslöser haben, muss aber nicht; ebenso die Order- und Positionsverwaltung. Eine Strategie ohne Auslöser lässt sich speichern, wird aber nicht ausgewertet (Anforderungen an den Strategiedesigner req-fach-015). |
| Anwendung einer Strategie | Die Zuordnung einer Strategie zu einem Konto und einem Instrument. Sie besteht, bis der Nutzer sie aufhebt. Dieselbe Strategie, zwei verschiedenen Instrumenten zugeordnet, sind zwei Anwendungen. Eine Anwendung kann über den Parameter `Instrument` ihrer Auslöser und Objekte und die Eigenschaft `Instrument` ihrer Orders auch weitere Instrumente verwenden und darauf handeln (req-fach-053). |
| Auswertung | Ein Durchlauf des Ablaufs einer Anwendung. Sie beginnt immer an einem Auslöser, zum Beispiel bei jedem Kerzenschluss, wenn die Strategie einen Auslöser dafür hat, oder beim Start von Hand mit dem Auslöser „Manuell“ (Anforderungen an den Strategiedesigner req-fach-015, Fachmodell req-fach-053). |
| Order- und Positionsverwaltung | Der Teil des Ablaufs nach dem Ausgang „gestellt“ von „Order aufgeben“. Er gilt für genau diese Order und die daraus entstehende Position, kann eigene Auslöser haben (Anforderungen an den Strategiedesigner req-fach-015) und besteht, bis die Order gelöscht oder abgelaufen oder die Position geschlossen ist. Englisch „order and position management“. Der Begriff wird nicht zu „Verwaltung“ verkürzt. |
| Order aufgeben | Das Element, das im Ablauf eine Order veranlasst. Es legt Ordertyp und Eigenschaften der Order fest und übergibt die Order an das Handelssystem. Es hat die Ausgänge „gestellt“ und „nicht gestellt“. |
| Order ändern | Das Element, das Preis, Stop-Loss, Take-Profit oder Gültigkeit einer wartenden Order ändert. Es hat die Ausgänge „geändert“ und „nicht geändert“. |
| Order löschen | Das Element, das eine wartende Order löscht. |
| Position ändern | Das Element, das Stop-Loss oder Take-Profit einer offenen Position ändert. Es hat die Ausgänge „geändert“ und „nicht geändert“. |
| Position schließen | Das Element, das eine offene Position ganz oder teilweise schließt. |
| Regelwerk | Eine benannte, geordnete Sammlung konfigurierter Regeln mit festgelegten Werten. Die Regeln behalten darin ihre Einzelergebnisse. |
| Verbindung | Ein Element in Form einer Linie zwischen zwei Elementen auf der Zeichenfläche, von einem Ausgang zu einem Eingang. Eine Verbindung ist eine Ablaufverbindung oder eine Datenverbindung; beide sind sichtbar unterschieden (req-ui-014). Das Wort „Kante“ wird nicht verwendet. |
| Ablaufverbindung | Eine Verbindung, die die Reihenfolge festlegt: „danach folgt“ im Ablauf, der wahr- oder falsch-Pfad einer Bedingung oder ein anderer Ausgang eines Elements des Ablaufs (req-ui-014). |
| Datenverbindung | Eine Verbindung, die den Weg eines Werts festlegt: von einer Eigenschaft eines Objekts auf der Zeichenfläche oder dem Ergebnis einer seiner Methoden zu einem Eingang eines anderen Elements, zum Beispiel einer Bedingung, einer Berechnung, „Order aufgeben“ oder dem Parameter eines anderen Objekts. Ihre Beschriftung nennt die übergebene Eigenschaft oder Methode; wo der Objekttyp es vorsieht, kann für die Verbindung das Aktualisieren eingeschaltet sein. Ein Ausdruck kann die Eigenschaft auch direkt über den Namen ansprechen; beide Wege führen zum selben Ergebnis (req-ui-014, Fachmodell req-fach-055). |
| Ausgang | Die Stelle eines Elements, an der eine Verbindung beginnt: für Ablaufverbindungen die Ausgänge des Ablaufs, zum Beispiel „wahr“ und „falsch“ einer Bedingung oder „gestellt“ und „nicht gestellt“ von „Order aufgeben“; für Datenverbindungen jede Eigenschaft und jede Methode eines Objekts auf der Zeichenfläche (req-ui-014, Fachmodell req-fach-055). |
| Eingang | Die Stelle eines Elements, an der eine Verbindung ankommen kann: beim Element des Ablaufs die Stelle für die ankommende Ablaufverbindung, außerdem jede Stelle, an der das Element einen Wert über eine Datenverbindung erhalten kann, zum Beispiel ein Parameter eines Objekts. Ein Eingang kann verbunden oder unverbunden sein; ein unverbundener Parameter erhält seinen Wert auf einem der anderen Wege nach req-fach-046. Ein verbundener Eingang erscheint im Ausdruck des Elements unter seinem Namen (req-ui-014, req-ablauf-007). |
| Eigenschaft | Alles, was ein Objekt beschreibt, ob vom Anwender eingestellt oder vom Objekt ermittelt. Die Richtung eines Trends ist eine Eigenschaft, auch wenn sie berechnet wird. |
| Parameter | Eine Eigenschaft, die der Anwender einstellt, zum Beispiel die Zeiteinheit eines Trends oder die Periode eines gleitenden Durchschnitts. |
| Methode | Eine Fähigkeit eines Objekts, die einen Wert zurückliefert. Eine Verwendung des Objekts übergibt entweder eine Eigenschaft oder das Ergebnis einer Methode. Welche Methoden ein Objekttyp hat, nennt seine Typbeschreibung. Die mitgelieferten Objekttypen haben vorerst keine Methoden; den Wert vor einer Anzahl Kerzen liefert „vorheriger Wert von“ (Fachmodell req-fach-055, req-fach-014). |
| Aktualisieren | Festlegung bei einer Verwendung einer Instanz, dass die Instanz ihre Werte neu ermittelt, bevor sie sie übergibt. Ohne Aktualisieren behält sie den Stand, den sie an der Stelle ihrer ersten Verwendung ermittelt hat; in einer Order- und Positionsverwaltung ist das für eine Instanz des Hauptablaufs der Stand beim Aufgeben der Order. Nur bei Objekttypen möglich, deren Typbeschreibung es vorsieht; in der Eigenschaftenansicht ein Schalter „Aktualisieren“ (Fachmodell req-fach-055, req-ui-014). |
| Ergebnis | Das, was eine Regel, eine Bedingung, eine Berechnung oder eine Methode eines Objekts liefert. Ein Objekt hat Eigenschaften; ein Ergebnis liefert es nur über seine Methoden (Fachmodell req-fach-055). Der Begriff „Ausgabe“ wird nicht verwendet. |
| Bindungsart | Die Art, wie ein Parameter seinen Wert erhält: fest in der Strategie eingetragen, aus einem Strategieparameter, durch eine Berechnung oder Regel bestimmt, erst bei der Anwendung übergeben, oder aus einer Eigenschaft eines anderen Objekts (Fachmodell req-fach-046). |
| Objektspeicher | Der Ort, an dem Strategien und Vorlagen dauerhaft abgelegt werden, getrennt von den übrigen Daten der Komponente. Als Einstellung wahlfrei: Objektverzeichnis oder Datenbank (Gesamtsystem req-system-012, req-system-015). |
| Objektverzeichnis | Ein Objektspeicher als Dateiverzeichnis mit einer Datei `<Kennung>.<Art>.json` je Objekt (Strategie oder Vorlage). Im Vorhaben `strategiedesign` die einzige Form des Objektspeichers. Der Pfad ist eine Einstellung von pipwerk Studio. Die Dateien sind die einzige Quelle der Objekte; eine Datei, die sich nicht lesen lässt, erscheint in der Liste als „nicht lesbar“ und wird nicht verändert. |
| Zeichenfläche | Der Bereich der Oberfläche, auf dem Elemente angeordnet und verbunden werden. |
| Eigenschaftenansicht | Der Bereich der Oberfläche, in dem die Eigenschaften des ausgewählten Elements angezeigt und seine Parameter geändert werden. |
| Konsistenzprüfung | Die Kontrolle einer Strategie oder einer Vorlage auf Vollständigkeit und Widerspruchsfreiheit, ohne sie auszuführen. Sie läuft beim Speichern und auf Anforderung und ist in der gemeinsamen Python-Bibliothek umgesetzt. Nicht zu verwechseln mit dem Prüfen durch eine Regel. |
| Pflichtparameter | Ein Parameter, der einen Wert haben muss, damit die Konsistenzprüfung keinen Fehler meldet. Welche Parameter Pflicht sind, legt der Objekttyp fest. Alle anderen Parameter sind optional. |
| Standardwert | Der Wert eines Parameters, den eine Vorlage vorgibt. Er wird beim Einfügen in eine Strategie von der Instanz übernommen und dort geändert. |
| Befund | Ein einzelnes Ergebnis der Konsistenzprüfung: eine Unstimmigkeit mit Stufe (Fehler oder Hinweis), Kennung des Befunds, dem betroffenen Element, der betroffenen Instanz oder Regel (oder keinem) und Angaben für den Text. Die Texte stehen in der Oberfläche, nicht in der Bibliothek. |
| Testfall | Eine Teststrategie, an der nachgewiesen wird, dass eine Funktion wie vorgesehen arbeitet. |
| Strategietester | Hauptkomponente, Produktname pipwerk replay. Führt Strategien gegen historische Kursdaten aus, in den Betriebsarten Einzelschritt-Test und Backtest (req-system-001, Anforderungen an den Strategietester). |
| Einzelschritt-Test | Betriebsart des Strategietesters, in der eine Strategie an historischen Kursdaten Schritt für Schritt abläuft, um zu prüfen, ob sie arbeitet wie gedacht. |
| Backtest | Betriebsart des Strategietesters, in der eine Strategie an historischen Kursdaten ohne Unterbrechung über einen Testzeitraum abläuft, und ein einzelner solcher Lauf. Ergebnis sind Kontoentwicklung, Trades und Kennzahlen. |
| Testlauf | Anwendung einer Strategie in einem Testzeitraum mit einem Testkonto, im Einzelschritt-Test oder im Backtest (req-test-001). |
| Testzeitraum | Zeitraum der historischen Kursdaten, über den ein Testlauf geht (req-test-002). |
| Testkonto | Benannter, gespeicherter Satz von Kontowerten für die Abwicklung eines Testlaufs: Anfangskapital, Kontowährung, Hebel, Spread, Kommission (req-test-005). |
| Interne Order | Order im Strategietester. pipwerk wickelt sie rechnerisch gegen historische Kurse ab, ein Broker erhält sie nicht (req-test-004). |
| Handelnde Stelle | Auswertung im Einzelschritt-Test, in der der Ablauf „Order aufgeben“, „Order ändern“, „Order löschen“, „Position ändern“ oder „Position schließen“ erreicht (req-test-011). |
| Datenbestand historischer Kursdaten | Von pipwerk geführter Bestand an Kerzen, Ticks und Angaben zum Instrument, aus dem der Strategietester liest. Der Anwender kann eine Reihe ganz oder für einen Zeitraum löschen, ebenso die Angaben zu einem Instrument je Broker, jeweils nach einer Rückfrage (req-system-025). |
| Import | Übernahme von Dateien im festgelegten Dateiformat in den Datenbestand historischer Kursdaten, beliebig viele in einem Vorgang, mit Fortschritt und Abbrechen (req-system-026). Der Anwender legt fest, ob die Dateien behalten werden; sonst entfernt die Komponente sie danach (req-system-028). |
| Ablageverzeichnis | Verzeichnis, in dem beim Import behaltene Dateien liegen. Die Komponente liest sie nicht wieder; um ihre Pflege kümmert sich der Anwender (req-system-028). |
| Ablageform | Die eine Form, in der eine Komponente ihre Daten für ihre Arbeit hält, für historische Kursdaten der Datenbestand historischer Kursdaten (req-system-028). |
| Abruf | Holen von Kursdaten und Angaben zum Instrument aus einer Quelle, zum Beispiel MetaTrader 5, als Dateien für den Import (req-system-027). Eine Anfrage an den Abruf und die Lieferung der Dateien laufen über pipwerk relay (Anforderungen an das Nachrichtensystem req-relay-007). |
| Nachrichtensystem | Produktname pipwerk relay. Überträgt Nachrichten zwischen eigenständig laufenden Komponenten, auch zwischen verschiedenen Rechnern (req-system-005, Anforderungen an das Nachrichtensystem). |
| Nachricht | Einheit, die über das Nachrichtensystem übertragen wird, mit Nachrichten-ID, Absender, Adressat, Priorität, Nachrichtenart, Inhalt und Bezug-Nachrichten-ID (Anforderungen an das Handelssystem req-grund-004). |
| Relay | Teil des Nachrichtensystems, der auf jedem Rechner läuft, auf dem eine Komponente Nachrichten sendet oder empfängt. Eine Komponente tauscht Nachrichten nur mit dem Relay ihres Rechners aus (req-relay-001, req-relay-002). |
| Übertragungsweg | Austauschbarer Weg, über den Nachrichten zwischen Komponente und Relay und zwischen Relays übertragen werden, zum Beispiel Matrix oder Dateien (req-relay-002, req-relay-003, req-relay-004). |
| Adressbuch | Liste eines Relays mit den Relays, die es kennt, je Relay mit dem Übertragungsweg, über den es erreichbar ist (req-relay-006). |
| Standard-Relay | Relay, an das ein Relay eine Nachricht weitergibt, wenn das zuständige Relay nicht in seinem Adressbuch steht (req-relay-006). |
| Laufende Komponente | Eine Komponente, die auf einem Rechner läuft und Nachrichten über das Nachrichtensystem sendet oder empfängt. Eine Komponente kann mehrfach laufen; jede laufende Komponente hat eine eigene Adresse (req-relay-005). Nicht zu verwechseln mit einer Instanz im Strategiedesigner. |
| Adresse | Eindeutige Bezeichnung einer laufenden Komponente im Nachrichtensystem aus drei Teilen: `<laufende Komponente>.<pipwerk-Netz>.<zuständiges Relay>`. Absender und Adressat einer Nachricht sind Adressen (req-relay-005, Anforderungen an das Handelssystem req-grund-004). |
| pipwerk-Netz | Teil der Adresse: Name des Netzes, zu dem das zuständige Relay gehört (req-relay-005). |
| Betreiber | Wer das Netz kontrolliert, in dem die Komponenten von pipwerk laufen, und dort zum Beispiel den Matrix-Server betreibt (req-system-011, req-relay-004). |

## Technische Begriffe

| Begriff | Bedeutung |
| --- | --- |
| Gemeinsame Python-Bibliothek | Das Python-Paket `packages/domain-core` (Paketname `pipwerk_domain`). Es enthält die fachlichen Objekte, ihre Prüf- und Rechenlogik und die Beschreibung der Elementtypen. pipwerk Studio, pipwerk replay und pipwerk trader binden es ein. |
| Typbeschreibung | Die maschinenlesbare Beschreibung eines Elementtyps oder Objekttyps mit den Feldern Kennung, Art (Auslöser, Element des Ablaufs, Objekttyp, Objekt der Anwendung, Ordertyp, Berechnungsverfahren des Trends), Beschriftung (Name und Beschreibung in Deutsch und Englisch), Parameter (Kennung, Datentyp, Pflicht oder optional, Standardwert, zulässige Werte, erlaubte Bindungsarten, Beschriftung), Eigenschaften (Kennung, Datentyp, MUSS oder KANN, Beschriftung; bei Ordertypen, ob der Anwender sie belegt), Methoden, ob der Objekttyp das Aktualisieren vorsieht (Fachmodell req-fach-055), Ausgänge, „Regeln zulässig“ und „auf Zeichenfläche“. Die Oberfläche baut daraus Elementbibliothek, Elemente und Eigenschaftenansicht auf. |
| Elementregister | Die Stelle in der gemeinsamen Python-Bibliothek, an der alle Elementtypen und Objekttypen (und die Berechnungsverfahren des Trends) angemeldet sind und von der sie nach Kennung oder als Liste abgefragt werden. Weitere Python-Pakete melden Typen über den Einstiegspunkt `pipwerk.element_types` an. |
| Strategiedokument | Die Darstellung einer Strategie als JSON-Text. Sie wird für Datei, Web-API und Nachrichten verwendet. |
| Strategiedatei | Eine Datei im Objektverzeichnis, die ein Strategiedokument enthält. Sie ist die verbindliche Fassung der Strategie. |
| Schema | Die formale Beschreibung, welche Felder ein Dokument enthalten muss und welche Werte zulässig sind. Pipwerk verwendet JSON-Schema. Schemata liegen versioniert unter `contracts/`. |
| Formatversion | Die Versionsnummer des Schemas, nach dem ein Dokument geschrieben wurde. Sie steht im Dokument und erlaubt, ältere Dateien später zu erkennen und zu überführen. |
| Index | Ein Verzeichnis der gespeicherten Objekte mit Kennung, Name und Beschreibung, das sich aus den Dateien neu aufbauen lässt. In pipwerk Studio gibt es keinen Index und keine Tabelle dafür in der Datenbank (Entscheidung E5): Ein Index wäre nur eine zweite Fassung derselben Daten. Die Dateien im Objektverzeichnis sind die einzige Quelle, das Backend liest sie bei Bedarf. Wird das zu langsam, kann später ein Index ergänzt werden. |
| Schnittstelle | Eine Stelle, an der Daten in ein Programm hinein- oder herauskommen: die Web-API, das Lesen und Schreiben von Dateien, das Lesen der Konfiguration. |
| Web-API | Die über HTTP erreichbare Schnittstelle einer Komponente. Jede Adresse darin heißt Endpunkt. Die öffentliche Web-API von pipwerk Studio liegt unter `/api/v1/` und ist unter `contracts/api/` beschrieben; die übrigen Endpunkte unter `/api/` sind interne Verbindungen der Komponente. |
| Testumgebung | Die auf dem Entwicklungsrechner aus dem Commit eines Arbeitspakets gestartete Komponente. Die QA prüft dort aus Kundensicht, der Auftraggeber erprobt dort und nimmt ab. |
| Entwicklungsrechner | Der Rechner, auf dem Arbeitsverzeichnisse, Testumgebungen und die Sitzungen von Softwarearchitekt, Entwicklungsleiter und Team liegen. |
| Vorhaben, Arbeitspaket, Auftrag, Übergabedokument, Meldung, Durchlauf | Begriffe des Entwicklungsprozesses, definiert im Entwicklungsverfahren (dev-werk, `de/process/development-process.md`, Abschnitt „Begriffe“). |

## Werkzeuge und Bibliotheken

| Name | Zweck in Pipwerk |

| FastAPI | Python-Bibliothek, mit der die Web-API einer Komponente gebaut wird. |

Aus ihren Modellen wird das JSON-Schema erzeugt. In der gemeinsamen Python-Bibliothek wird sie nur im Teilpaket für Dokumente (`pipwerk_domain.documents`) verwendet; das Objektmodell besteht aus einfachen Python-Klassen ohne Pydantic. |

| Alembic | Werkzeug zu SQLAlchemy, das Änderungen am Datenbankaufbau versioniert durchführt. Eine bestehende Datenbank wird damit auf einen neuen Aufbau gebracht, ohne sie neu anzulegen. |
| pytest | Werkzeug für automatische Tests von Python-Code. |
| React, TypeScript, Vite | Grundlage der Browseroberfläche: React für die Bedienelemente, TypeScript als Programmiersprache, Vite zum Bauen und für den Entwicklungsbetrieb. |

| i18next | Bibliothek für die deutschen und englischen Texte der Oberfläche. |
| TanStack Query | Bibliothek, mit der die Oberfläche Daten der Web-API abruft und zwischenspeichert. |
| Vitest, Testing Library | Werkzeuge für automatische Tests der Oberfläche ohne Browser. |
| Playwright | Werkzeug für automatische Tests in einem echten Browser. Es bedient die Oberfläche wie ein Nutzer. |
| Ruff, mypy | Werkzeuge, die Python-Code auf Stil und Typfehler prüfen. |
| uv | Werkzeug, das Python-Pakete installiert und ihre Versionen festschreibt. |
